# ระบบสลิป PromptPay

## ขั้นตอนฝั่งสมาชิก

1. เลือกแพ็กเกจ → ระบบสร้างออเดอร์ (กดซ้ำไม่สร้างใบใหม่ ใช้ใบที่ยังไม่ได้แนบสลิปต่อ)
2. สแกน QR PromptPay ที่ระบบสร้างให้ (ยอดเงินฝังมาในโค้ดแล้ว)
3. แนบรูปสลิป → สถานะเป็น "รอตรวจสลิป"
4. แอดมินอนุมัติ → เปิดสิทธิ์ + ส่งใบเสร็จทางอีเมล

## บัญชีรับเงิน และสวิตช์เปิด/ปิดรับชำระเงิน

ตั้งบน Vercel production ทั้งหมด (ไม่อยู่ในโค้ด) — **ตั้งเป็นแบบ non-sensitive ตั้งใจ** อ่านกลับด้วย `vercel env pull` ได้
ไม่ใช่ความลับอยู่แล้ว เลขพร้อมเพย์ฝังอยู่ใน QR ที่ลูกค้าทุกคนสแกน

| env | ค่า (ตั้ง 29 ก.ย. 2569) | ใช้ทำอะไร |
|---|---|---|
| `PROMPTPAY_ID` | `004999228199112` | สร้าง QR ตามยอด + ตรวจบัญชีผู้รับบนสลิป |
| `PROMPTPAY_NAME` | `นาย ณัฐฤกษ์ ขอคตสำโรง` | ชื่อที่หน้าชำระเงินโชว์ว่า "เข้าบัญชี …" |
| `NEXT_PUBLIC_SALES_PAUSED` | `0` | เปิดรับชำระเงิน — ไม่ตั้ง / ตั้ง `1` = ปิด (ค่าโดยปริยายในโค้ดคือปิด) |

**เลขพร้อมเพย์มาจากไหน:** ถอดจาก QR "รับเงิน" ของ K PLUS (บัญชีกสิกร xxx-x-x0543-x) — เป็นเลขอ้างอิง 15 หลัก
ชนิด e-Wallet (tag 29 ย่อย 03) ไม่ใช่เบอร์โทรหรือเลขบัตร ตรวจแล้วว่า `promptpay-qr` สร้าง tag 29 ตรงกับ QR ของ K PLUS ทุกตัว
เปลี่ยนบัญชีครั้งหน้า: ถอด QR ใหม่ (`cv2.QRCodeDetector` อ่านได้) เอาค่าใน tag 29 มาใส่ ห้ามพิมพ์เลขบัญชีธนาคารตรง ๆ

**เงินที่โอนผ่านเว็บก่อน 29 ก.ย. 2569 ~19:50 เข้าบัญชีเดิม** — คืนเงินให้ลูกค้าช่วงนั้นต้องคืนจากบัญชีเดิม
(`PROMPTPAY_ID` เดิมตั้งเป็น sensitive ไว้ อ่านกลับไม่ได้ ถ้าจะสลับกลับต้องถามเจ้าของบัญชี)

**เปลี่ยนค่าแล้วต้อง deploy ใหม่** (`NEXT_PUBLIC_*` ถูกฝังตอน build):
```bash
vercel env update PROMPTPAY_ID production --value <เลข>
vercel redeploy <url ของ production ตัวล่าสุด> --target production
```
เช็กก่อน redeploy ว่าไม่มี deploy ค้างอยู่ (`vercel ls`) และตัวที่ใช้อยู่ตรงกับ commit ล่าสุดบน main
ไม่งั้น redeploy ตัวเก่าไปทับของใหม่ที่อีกเครื่องเพิ่ง deploy

**ทดสอบหลังเปลี่ยนบัญชี:** สร้างออเดอร์เอง สแกน QR ด้วยแอปธนาคาร ดูชื่อผู้รับ แล้วกดยกเลิก ไม่ต้องโอนจริง

## การกันสลิปซ้ำ (ทำงานเสมอ ไม่ต้องตั้งค่า)

| ชั้น | กันอะไร |
|---|---|
| `slipHash` (sha256 ของไฟล์) | ส่งรูปสลิปเดิมซ้ำอีกออเดอร์ |
| `transRef` (เลขอ้างอิงจากสลิป) | ถ่ายรูปสลิปเดิมใหม่แล้วส่งซ้ำ — ใช้ได้เมื่อเปิดระบบตรวจอัตโนมัติ |

ทั้งสองคอลัมน์เป็น unique ระดับฐานข้อมูล ต่อให้โค้ดพลาดก็ยังซ้ำไม่ได้

## ตรวจสลิปอัตโนมัติ (ไม่บังคับ)

ระบบต่อกับ [EasySlip](https://easyslip.com) ไว้ให้แล้ว เปิดใช้โดยใส่โทเคน:

```bash
vercel env add EASYSLIP_TOKEN
```

เปิดแล้วทุกสลิปที่แนบเข้ามาจะถูกอ่านยอดและเทียบกับออเดอร์ ผลจะขึ้นเป็นป้ายในหน้า `/admin/orders`:

| ป้าย | หมายถึง |
|---|---|
| ยอดตรง | อ่านสลิปได้และยอดตรงกับออเดอร์ |
| ยอดไม่ตรง | อ่านได้แต่ยอดไม่ตรง — ดูให้ละเอียดก่อนอนุมัติ |
| สลิปซ้ำ | สลิปหรือเลขอ้างอิงนี้ถูกใช้ไปแล้ว (ระบบปฏิเสธตั้งแต่ตอนแนบ) |
| อ่านสลิปไม่ได้ | ภาพเบลอ/ครอบตัด หรือผู้ให้บริการมีปัญหา — ตรวจด้วยตาเหมือนเดิม |

**ผลตรวจไม่ผ่านไม่ทำให้ออเดอร์ถูกปฏิเสธอัตโนมัติ** — แค่ติดธงไว้ให้คนตัดสินใจ
เพราะการอ่านสลิปพลาดได้ และการปฏิเสธผิดตัวแพงกว่าการเสียเวลาดูเอง

### อนุมัติอัตโนมัติเมื่อยอดตรง

```bash
vercel env add SLIP_AUTO_APPROVE   # "true"
```

เปิดแล้วสลิปที่ยอดตรงจะเปิดสิทธิ์ให้ทันทีโดยไม่ต้องรอแอดมิน
แนะนำให้เปิดหลังจากใช้งานแบบตรวจมือมาสักพักแล้วมั่นใจว่าผลตรวจแม่นพอ

> ⚠️ ระบบเทียบเฉพาะ **ยอดเงิน** ไม่ได้เทียบว่าโอนเข้าบัญชีเราจริงหรือไม่
> ก่อนเปิด auto-approve ควรตรวจสอบสัญญา API ของผู้ให้บริการกับเอกสารล่าสุด
> และเทียบชื่อ/เลขบัญชีผู้รับเพิ่ม ถ้าต้องการความเข้มงวดกว่านี้

## ทำไมรูปสลิปยังเก็บใน DB

เก็บเป็น base64 ในคอลัมน์ `slipData` — Postgres ย้ายค่าใหญ่ออกไปเก็บนอกแถว (TOAST) ให้เอง
จึงไม่ช้าตราบใดที่ **ไม่ select คอลัมน์นี้ในหน้ารายการ**

หน้า `/admin/orders` และ `/account/orders` จึงระบุ `select` เฉพาะฟิลด์ที่ใช้
ส่วนรูปโหลดทีละใบผ่าน `/api/admin/slip/[id]` (เฉพาะ ADMIN, ห้ามแคช)

ถ้าอนาคตออเดอร์เยอะจนอยากย้ายรูปออกจากฐานข้อมูลจริง ๆ จุดที่ต้องแก้มีที่เดียว
คือ `submitSlip` กับเส้นทางรูปด้านบน
