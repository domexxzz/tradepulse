## อาการที่เข้ามา

กลุ่ม Admin QVX ได้ข้อความซ้ำเป็นคู่ ทุก 15–16 นาที ติดกันหลายวัน

```

03:08  ⚠️ บอท TradingView ให้สิทธิ์ไม่สำเร็จ — @Kiadthawee

03:23  ⚠️ ... (ข้อความเดิมเป๊ะ)
```

ลูกค้าสองราย: `@Kiadthawee` และ `@Tradingview201915`

เรื่องสำคัญคือ **เคยใส่ตัวกันไปแล้วสองรอบ และทั้งสองรอบตัวกันเองก็พัง**
- รอบแรก: เทียบเวลาจาก `createdAt` ซึ่งไม่ขยับ → เพิ่ม `lastDispatchedAt`
- รอบสอง: ใส่ `failCount` + เพดาน 5 ครั้ง แต่ก็ยังวนอยู่

## ต้นเหตุจริง (รอบสาม)

`syncTradingViewGrant` ถือว่า **"บอทรับงานเข้าคิว" = "สำเร็จ"** แล้วเซ็ต
`failCount: 0, lastFailReason: null` ทุกครั้งก่อนรู้ผลจริง

บอทรับงานเสมอ (Selenium กินเวลาเป็นนาที จึงเข้าคิวก่อนแล้วยิงผลกลับทาง callback)
บรรทัดเดียวนี้จึงทำให้ตัวกันทั้งสามชั้นตายพร้อมกัน:

| ตัวกัน | ทำไมตาย |
|---|---|
| เพดาน `MAX_FAILS = 5` | ตัวนับถูกรีเซ็ตทุกรอบ ไม่มีวันถึง 5 |
| ตัวกันเตือนซ้ำใน callback | เทียบ `lastFailReason` กับ `null` ทุกครั้ง เห็นเป็น "เหตุผลเปลี่ยน" |
| เวลารอใน reconcile | เห็น `failCount: 0` แล้วเข้าทางลัด `queue === 0` ข้ามเวลารอ |

**บทเรียน: อย่าเขียน "สำเร็จ" ลงฐานข้อมูลก่อนที่จะรู้ผล**
และอย่ามีตัวกันหลายตัวที่อ่านคนละค่า เพราะโค้ดอีกบรรทัดล้างค่านั้นทิ้งได้

## ที่แก้

### ต้นเหตุ
- `src/lib/lifecycle.ts` — ล้างตัวนับได้เฉพาะตอนสำเร็จจริง (บอททำเสร็จทันที
  หรือ callback ตอบสำเร็จ) ตอนแค่เข้าคิวจดแต่ `lastDispatchedAt`
- `src/lib/reconcile.ts` — ทิ้งทางลัด "คิวว่าง = ข้ามเวลารอ" เปลี่ยนเป็นรอสั้นลง
  เหลือ `IDLE_REDISPATCH_MINUTES = 10` แทน (ปกติ 30)
  **เงื่อนไขที่เป็น "เร็วขึ้น" ปลอดภัยกว่า "ข้ามทิ้ง" เสมอ เพราะยังมีเพดานกั้นอยู่**
- `src/app/api/tradingview/callback/route.ts` — เคยหยิบคิวแบบไม่กรองสถานะเลย
  ตอนนี้ใช้ `ACTIVE_GRANT_STATUSES` (ประกาศที่ `lifecycle.ts` ที่เดียว) ร่วมกับที่อื่น
  ไม่งั้นผลจะไปลงคนละแถวกับแถวที่ถูกสั่งงาน แล้วตัวกันก็ไม่มีผลอีก

### กันไม่ให้เกิดเป็นครั้งที่สี่
- **`src/lib/alert-throttle.ts` + ตาราง `AlertThrottle`** — ด่านสุดท้ายระดับโครงสร้าง
  ตัดสินจาก **ข้อความที่จะส่งออกจริง** เท่านั้น ไม่สนว่าบั๊กอยู่เส้นทางไหน
  - คีย์เดิม + เนื้อเดิม + ยังไม่พ้น 6 ชม. → ไม่ส่ง นับไว้
  - เนื้อเปลี่ยน → ส่งทันที (จึงไม่กลายเป็นตัวกลบเรื่องใหม่)
  - พ้นเวลา → ส่งซ้ำได้ พร้อมบอกว่า "เรื่องเดิมเกิดซ้ำอีก N ครั้งระหว่างนี้"
  ใช้แล้วที่: การเตือนบอทให้สิทธิ์ไม่สำเร็จ และข้อความ "🔧 ระบบไล่งานค้าง"
- **`/api/cron/reconcile?dry=1`** — ดูว่ารอบนี้จะหยิบใคร เพราะอะไร โดยไม่สั่งบอท
  และไม่เตือนใคร ก่อนหน้านี้การตรวจสอบต้องรันของจริง = สแปมเพิ่มทุกครั้งที่อยากรู้

### เจอเพิ่มจาก dry-run
`@Tradingview201915` มี `failCount: 2` ด้วยเหตุผล "ติดต่อบอทไม่ได้" ขณะที่บอทยังดีอยู่
มันแค่ **ไม่ว่าง** — แยกใหม่:
- `TvResult.unreachable` = ท่อขาด ลองใหม่ทีหลังแล้วได้ **ห้ามกินโควตาเลิกลอง**
- บอทปฏิเสธงาน = คำตัดสิน ต้องนับและต้องเลิกลอง

นับรวมกันแปลว่าลูกค้าที่ชื่อถูกต้องถูกตัดทิ้งเพราะจังหวะที่บอทไม่ว่าง 5 หน

### ฝั่งลูกค้า
`/account/tradingview` เคยขึ้น "กำลังดำเนินการ ปกติไม่เกิน 24 ชม." **ทุกกรณี**
ที่สถานะเป็น PENDING รวมถึงตอนที่ชื่อไม่มีอยู่จริงบน TradingView — รออีกกี่วัน
ก็ไม่มีอะไรเกิดขึ้น หน้าเว็บเป็นคนบอกให้ลูกค้ารอของที่ไม่มีวันมา
ตอนนี้บอกตรง ๆ พร้อมวิธีหา username ที่ถูก และแก้ชื่อใหม่ = เริ่มนับใหม่

### CI
`verify` ยก Postgres เป็น service container จาก `postgres:16` บน Docker Hub
ซึ่งจำกัด pull ต่อ IP สำหรับคนไม่ล็อกอิน และ runner ของ GitHub ใช้ IP ร่วมกันทั้งโลก
พอโควตาหมด `verify` ล้มที่ **Initialize containers** ก่อนถึง step แรกด้วยซ้ำ
แล้ว `deploy` ที่ `needs: verify` ก็ไม่รันตามไปด้วย — **โควตาของคนแปลกหน้า
กลายเป็นตัวกั้น production ของเรา** ตัวแก้วันนี้ค้างอยู่สองรอบเพราะเรื่องนี้

เปลี่ยนไปใช้ Postgres ที่ติดมากับ runner อยู่แล้ว ไม่ต้องดึงจากที่ไหน

## วิธีตรวจว่ายังดีอยู่

```bash
# จากเครื่องที่ ssh ถึงคอมเฟิร์สได้ (CRON_SECRET อยู่ที่ C:\BotTV\cron_secret.txt)
# ดูว่ารอบนี้จะหยิบใคร เพราะอะไร — ไม่สั่งบอท ไม่เตือนใคร
GET /api/cron/reconcile?dry=1&secret=<CRON_SECRET>
```

สิ่งที่ควรเห็นเมื่อระบบปกติ:
- `willDispatch: 0` เมื่อทุกคิวเพิ่งถูกสั่งไป
- `duplicateQueues: []` — ถ้าไม่ว่าง แปลว่าลูกค้าคนเดียวมีคิวหลายแถว
  แต่ละส่วนของระบบอาจหยิบคนละแถว ต้องไปดู
- `failCount` ของงานที่ค้างต้อง **เพิ่มขึ้นเรื่อย ๆ** ไม่ใช่กลับเป็น 0
  ถ้ากลับเป็น 0 แปลว่าบั๊ก "เขียนสำเร็จก่อนรู้ผล" กลับมาแล้ว
