## สาเหตุ — ทางลัดเดียวกันสามจุด

ทุกจุดคือ "เห็นสถานะเดิมแล้วถือว่าเรียบร้อย" ซึ่งเงียบสนิทและไม่มีคิวให้ใครเห็น

### 1. ต่ออายุก่อนหมดอายุ = ไม่มีใครสั่งบอทเลย

`syncTradingViewGrant` ค้นคิวด้วย `status in [PENDING, PENDING_REVOKE, REVOKED]`
คนที่เคยได้อินดิเคเตอร์แล้วมีสถานะ `GRANTED` ซึ่ง **ไม่อยู่ในรายการ** → `findFirst` คืน `null`
→ `if (!grant) return` → บอทไม่เคยได้รับคำสั่ง → วันหมดอายุบน TradingView ยังเป็นวันเดิม

`ensureAccessGrant` ก็ไม่สร้างแถวใหม่ให้ เพราะมันกันซ้ำด้วย `status in [PENDING, GRANTED]`
และ `reconcile` ไม่หยิบ เพราะมันไล่เฉพาะ `PENDING` — ไม่มีใครมาเก็บเคสนี้เลย

> บั๊กเดียวกันเคยโดนที่เส้นทาง **เปลี่ยน username** แล้วแก้เฉพาะหน้าด้วยการตั้งคิว
> กลับเป็น `PENDING` ก่อนเรียก (`api/cron/delivery`) ตรงนั้นจึงรอด แต่เส้นทางต่ออายุไม่ได้ทำ

### 2. `ADDED` ในระบบ ≠ อยู่ในกลุ่มจริง

`ensureTelegramInvite` เดิม: `if (!dropped && (grant.status === "ADDED" || grant.inviteLink)) return;`
ลูกค้าออกจากกลุ่มเอง หรือถูกเตะตอนหมดอายุแล้วอัปเดตสถานะไม่ทัน สถานะก็ยังค้าง `ADDED`
ตอนต่ออายุจึงไม่มีใครออกลิงก์ใหม่ และ `backfillTelegramInvites` ก็ไม่หยิบ
(มันหยิบเฉพาะ `PENDING` ที่ `inviteLink` ว่าง) → ค้างถาวรจนลูกค้าทักมาเอง

นอกจากนี้ลิงก์เชิญมีอายุแค่ **7 วัน** (`INVITE_DAYS`) ใบของรอบก่อนตายไปแล้ว
แต่โค้ดเดิมนับว่า "มีลิงก์แล้ว" จึงข้ามการออกใบใหม่

### 3. คิวถอนที่ค้างจะถอนสิทธิ์คนที่เพิ่งจ่ายเงิน

หมดอายุแล้วบอทถอนไม่สำเร็จ คิวค้างที่ `PENDING_REVOKE` แล้ว `retryPendingRevokes`
สั่งถอนซ้ำทุกรอบ cron (ทุก 10 นาที) ถ้าลูกค้าต่ออายุระหว่างนั้น เราเพิ่งสั่งเพิ่มสิทธิ์ให้
แล้วรอบถัดไปจะถอนออกให้เอง — **สิทธิ์หลุดประมาณ 10 นาทีหลังจ่ายเงิน**
ฝั่ง Telegram ก็เหมือนกัน `PENDING_REMOVE` ที่ค้างคือใบสั่งเตะคนที่จ่ายเงินแล้วออกจากกลุ่ม

### ทำไม UAT ชุดนี้ต้องดักที่ขาออก HTTP ไม่ใช่ที่ฟังก์ชัน

บั๊กตัวจริงไม่ได้อยู่ในตรรกะของฟังก์ชันใดฟังก์ชันหนึ่ง มันอยู่ที่ **ลำดับการเรียกระหว่างฟังก์ชัน** —
`ensureAccessGrant` ไม่สร้างเพราะเห็น `GRANTED` และ `syncTradingViewGrant` ไม่สั่งเพราะหา `GRANTED` ไม่เจอ
ทั้งคู่ทำงานถูกตามสเปคของตัวเอง เทสต์ที่ mock ฟังก์ชันพวกนี้จึงจับไม่ได้

จึงถามคำถามเดียวที่สำคัญคือ **"บอทได้รับคำสั่งหรือไม่"** ซึ่งวัดได้ที่ขาออก HTTP เท่านั้น
`uat/renewal.uat.ts` แทน `globalThis.fetch` แล้วเก็บทุก request ที่ยิงออก
ตอบแทนบริดจ์บอทและ Telegram API ให้เหมือนของจริง (`{ok:true,queued:true}` / `createChatInviteLink` / `getChatMember`)

> **กับดักที่ต้องระวังที่สุดในไฟล์นั้น:** `tvAutoGrantEnabled` และ `telegramGroupManaged`
> อ่าน env ตอนโหลดโมดูล ถ้า `import` ก่อนตั้ง env จะได้ `false` แล้วทุกอย่างถูกข้ามเงียบ ๆ

  -H "Authorization: Bearer $CRON_SECRET" -H 'Content-Type: application/json' \

> ⚠️ **ห้ามสั่งทุกคนในรอบเดียว** รอบแรกที่ปล่อยไปไม่มีเพดาน แล้ว dry-run ขึ้นว่าจะสั่ง **200 ราย**

> รอบ "ทุกคน" ข้ามคนที่เพิ่งถูกสั่งไปใน 30 นาที จึงสั่งซ้ำแล้วเดินหน้าไปเรื่อย ๆ ไม่วนคนเดิม

## ภาคต่อ — ทำไมคำสั่งซ่อมไม่มีใครได้ผลกลับมา

สั่ง `resync` ซ่อม 7 ราย แล้วเฝ้ารอ 22 นาที **บอทยืนยันกลับมา 0 ราย** ไล่ดูพบว่า:

```
คิวบอท = 370 งาน
15:11:54 คิวบอท = 369
15:12:39 คิวบอท = 368
15:13:25 คิวบอท = 366
15:14:13 คิวบอท = 394     ← +28 ใน 45 วินาที
```

`retryPendingRevokes` ใน `src/lib/reconcile.ts` **ไม่มีเวลารอและไม่มีเพดานเลิกลอง**
ต่างจาก `retryPendingGrants` ที่มีครบทั้งสองอย่าง:

- หยิบ `PENDING_REVOKE` 15 แถวที่เก่าสุดทุกรอบ cron (`bridge-health.yml` รันทุก 10 นาที)
- ไม่ดู `lastDispatchedAt` เลย
- บอทเกือบทุกครั้งตอบ `queued = true` (รับเข้าคิว ยังไม่ทำ) แถวจึงคาสถานะ `PENDING_REVOKE`
- รอบหน้าหยิบ **ชุดเดิมทั้ง 15 คน** ซ้ำ → วนไม่จบ ≈ **90 งานขยะต่อชั่วโมง**

บอททำได้ทีละคน 60-120 วินาที คิว 370 งาน = **6+ ชั่วโมง** ลูกค้าที่เพิ่งจ่ายเงินต่อคิวอยู่ข้างหลังนั้น

> บั๊กตัวเดียวกันเคยเกิดกับ **คิวให้สิทธิ์** แล้วแก้ไปตั้งแต่ 30 ก.ย. / 10 ต.ค. 69
> ด้วย `lastDispatchedAt` + `failCount` + `MAX_FAILS` แต่ไม่มีใครย้อนกลับมาแก้ฝั่งถอน

แก้: ใส่เวลารอ (ใช้ความลึกคิวบอทร่วมกับฝั่งให้สิทธิ์) · เพดาน `MAX_FAILS` · จด `lastDispatchedAt`
ก่อนยิงเสมอ · นับความล้มเหลวเมื่อบอทปฏิเสธงาน (ไม่นับตอนติดต่อบอทไม่ได้)

และ `inspectReconcile` เดิม**ส่องเฉพาะคิวให้สิทธิ์** ตอนไล่บั๊กมันจึงรายงาน `willDispatch: 0`
อย่างมั่นใจขณะที่คิวบอทกำลังบวม — เครื่องมือวินิจฉัยที่มองไม่เห็นครึ่งระบบทำให้เชื่อผิดได้แรงกว่าไม่มีเลย
เพิ่ม `willRevoke` · `pendingRevokeTotal` · `revokes[]` เข้าไปแล้ว

## บทเรียน

**สถานะในฐานข้อมูลเป็นคำบอกเล่า ไม่ใช่ความจริง** — `GRANTED` คือ "เราเคยสั่งสำเร็จ"
ไม่ใช่ "สิทธิ์ยังไม่หมดวัน" และ `ADDED` คือ "เคยเข้ากลุ่ม" ไม่ใช่ "ยังอยู่ในกลุ่ม"
ทุกครั้งที่โค้ด `return` เพราะสถานะดูเรียบร้อย ต้องถามว่า **ใครจะมาเก็บเคสนี้ถ้ามันไม่จริง**
ถ้าคำตอบคือ "reconcile" ให้เช็กด้วยว่า reconcile หยิบสถานะนั้นจริงหรือเปล่า — คราวนี้มันไม่หยิบ
